### 2.1 V1.2 给模块槽配了一条独立 I²C 总线（confirmed，源码层）

BSP 源码 `components/esp-mosaico-bsp/include/bsp/esp_mosaico.h:62-75`（**2026-09-21 按 Hiro H0 F03 整改**：原写 `components/esp-mosaico-bsp/onboard/esp_mosaico.h:63-75`，路径与起始行均有误；该头文件位于 `include/bsp/` 下，`onboard/` 下的是 `.c` 实现）：

```
/* Mainboard I2C bus. Legacy aliases below retain the v1.0 pin values. */
#define BSP_I2C_PORT              I2C_NUM_0
#define BSP_I2C_SDA_V1_0          GPIO_NUM_0
#define BSP_I2C_SCL_V1_0          GPIO_NUM_1
#define BSP_I2C_SDA_V1_2          GPIO_NUM_56
#define BSP_I2C_SCL_V1_2          GPIO_NUM_3
#define BSP_I2C_SDA               BSP_I2C_SDA_V1_0
#define BSP_I2C_SCL               BSP_I2C_SCL_V1_0

/* v1.0 shares I2C0 with the mainboard; v1.2 uses a dedicated I2C1 bus. */
#define BSP_SUBBOARD_I2C_PORT_V1_0 I2C_NUM_0
#define BSP_SUBBOARD_I2C_PORT_V1_2 I2C_NUM_1
#define BSP_SUBBOARD_I2C_SDA       GPIO_NUM_0
#define BSP_SUBBOARD_I2C_SCL       GPIO_NUM_1
```

**V1.0 时主板与模块槽共用 I²C；V1.2 把主板总线搬到 GPIO56／GPIO3，把 GPIO0／GPIO1 整条留给模块槽，跑在 `I2C_NUM_1` 上。**

直接后果：此前反复引用的「共享总线已占用 `0x11 0x12 0x19 0x55 0x5A 0x69`」这条约束，**在 V1.2 上不再施加于模块总线**（这些是主板侧器件，已随主板总线迁至 GPIO56／3）。

**（2026-09-21 按 Hiro H0 F03 整改）** 原写「模块总线上只有 `0x50`／`0x51`，底座选址几乎不受限」已改为：**BSP 模块管理器在这条总线上已注册的 EEPROM 地址为 `0x50`（左槽）／`0x51`（右槽）；左右两槽共用同一条模块总线，其他模块的器件地址（官方模块板上的器件、将来另插模块的器件）仍须管理**，不能写成「总线上只有两个地址」。底座选址须在这一约束下确认，不是「几乎不受限」。Chrome 的 `review/chrome/D1-module-interface/LEFT_SLOT.md:38` 原文已写「实际另插模块的地址仍须管理」，是正确的；**错误在本文的转述，不在 D1**。

代价（源码层可核）：腾出 GPIO56 与 GPIO3 的代价是砍掉 V1.0 的 codec 电源控制脚与状态 LED，两者在 V1.2 上分别变为 always-on 与不可用。

### 2.2 模块槽同时提供 I²C、5V 供电输入与足量 GPIO（源码层 confirmed ＋ V1.2 电气 ASSUMPTION）

模块槽 pin16／pin14 为 `GPIO0`＝SDA ／ `GPIO1`＝SCL；pin17 为 `5V_IN`，**V1.0 官方引脚表**注明「External 5 V input (can power and charge the device)」。左槽 12 根 GPIO 为 `{55,53,19,48,18,13,17,12,16,14,15,4}`，扣除作 EEPROM 地址选择的 `GPIO14` 后仍有 11 根，足够 D-pad 4 ＋ ABXY 4 ＋ L/R 2 共 10 键各占一根，余 1 根。

左槽这 12 根与板载 I²S 集合 `{54,37,49,52,40}` 交集为空；右槽的 GPIO49／52／54／37／40 与 I²S 复用，占用会使扬声器与麦克风失效。**这里只证明与板载 I²S 无引脚冲突，不是宣称与任何其他外设或未来驱动都不冲突。** 因此底座**优先考察左槽**；左右槽取舍还涉及摄像头的槽位竞争，属用户决策 UD-A（见 §5）。

**（2026-09-21 按 Hiro H0 F03 整改）** 本项**不整项 confirmed**，拆分如下：

- **源码可核事实**：12 根 GPIO 集合、与 I²S 集合交集为空、`GPIO14` 用作左槽 EEPROM 地址选择（输出 0 → 7-bit `0x50`）。
- **V1.0 官方文本事实**：H2 二十脚定义、pin17 为 `5V_IN` 且注明可供电并充电、pin19 为 3.3 V、pin18 为 NC。
- **ASSUMPTION（对应派发项 A-H0-1）**：把上述 20 脚定义、供电与充电路径**逐脚沿用到 V1.2 实物**。**未经实物逐网导通核对**；BSP 的 GPIO 映射只能证明软件如何驱动，**不能证明物理铜线走向、插接朝向与 pin1 位置**。pin17 的电压容差、持续／峰值电流与反灌边界仍为 **unknown**，Chrome 的 `DOCUMENT_BOUNDARIES.md:13–18` 保留 unknown 是正确的，本文不借预算数字填充额定。

MakerWorld 模型页外壳实拍图上，中框模块槽正上方印有逐脚引脚标签，与 V1.0 用户指南的 H2 表逐脚一致。**（2026-09-21 按 Hiro H0 F03 整改）** 原写「说明 2×10P 的引脚定义在 V1.2 上未改」已降为 **derived**：外壳印字一致是有价值的旁证，但**不能证明板内的逐脚铜线、电源路径与保护器件一致**，也未确定该实拍样本的版次。

### 2.3 BSP 关键词检索记录（仅为检索记录，不构成功能排除结论）

**（2026-09-21 按 Hiro H0 F03 整改）** 本节原标题为「背部焊盘在 BSP 中没有任何软件支持」，并据此写出「背部焊盘从来没有软件支持；其用途只能靠万用表实测确定」。**该结论已删除**，理由（Hiro §3 证据表、§4 第 2.3 项）：

- 检索命中的是**字符串**，不是电气网络。即便复跑仍得零命中，背部触点若挂在既有 I²C 或 GPIO 上，也会由**通用驱动**处理，源码中本就无须出现 `rear pad`／`pogo` 之类字样。**「关键词零命中 → 从无软件支持」是不成立的推论**；**仅补上 grep 日志不能关闭这一逻辑问题，只把标签改成 derived 同样不够**。
- 「用途只能靠万用表实测确定」也过宽：官方图纸与原理图同样可以提供证据。

**保留的事实范围**：曾对 BSP 全部 32 个 commit 执行 `git grep`（back pad／pogo／rear pad／expansion pad／4-pad／磁吸／260710／260821），记录为零命中。其可主张的结论仅为「**这些关键词未出现在该 BSP 源码中**」。该检索**本轮未复跑、未留存日志**（Hiro §2 明列为未检查项），复跑并留证后也只能支持上述这一句话。背部触点的存在与用途仍为 **unknown**，须由实物与官方图纸判定。

## 3. 我错在哪

方案 H 的出发点是「V1.2 背面没有 I²C，所以按键要走 UART，所以需要 MCU」。**错在前提选择**：我把「背面」当成了唯一通路，而**官方为扩展准备的接口是模块槽**，那里同时提供 I²C、5V 输入与可用 GPIO，V1.2 还给它配了独立总线。

**我绕开了一个为此而设计的接口，然后为了绕开它而增加了一颗芯片，并据此让用户修订了需求。**

直接原因是检索顺序：我先用第三方照片认定「背面四焊盘消失」，随即把注意力锁死在背面，而没有先去读 BSP 源码里模块槽在 V1.2 上发生了什么。**新证据出现时应当重新检视前提，而不是在既定前提上继续推演。**

**（2026-09-21 按 Hiro H0 F02／F03 整改）** 此处两点需同步收窄：① 「背面四焊盘消失」应表述为「现有 V1.2／260821 图像未见 V1.0 中央四触点」，见 §4 表 A 行；② 「I²C、供电、GPIO 一应俱全」是**源码与 V1.0 文本层面的一应俱全**，V1.2 实物的逐脚电气仍是假设，见 2.2。**第三次错误不要变成「把模块槽当成唯一通路」。**

- **模块槽 EEPROM 从 pin19（3.3 V）取电、pin18 为 NC、不从底座送 3.3 V 进主机**，这一点与 Chrome 的 D1 一致；但由此**不能反推「主机未初始化时 pin19 必定无压」**，底座侧的反灌与限流设计不得建立在该反推之上。

## 6. 仍未解除的未知

- 模块槽连接器的机械形态与插拔特性（对应 `E-01`）。**（2026-09-21 按 Hiro H0 F04 整改）** 原写「方案 G 对此不敏感」已撤回：G 降低的是插拔次数，**对 E-01 的几何仍然敏感**——连接器的轴向／侧向形态决定插接方向、固定方式、整体外形与 USB-C 避让，且装配、振动与侧向载荷始终存在。E-01 仍须实物确认。
- 模块 PCB 上连接器各脚是否可引出（第二级魔改的前提）。
- `5V_IN` 的实际载流能力：V1.0 官方文字称可供电并充电，但**未给电流数值**；电压容差、持续／峰值电流、浪涌与反灌路径均为 unknown，**不以任何预算数字代替额定**。
- **版次映射（2026-09-21 按 Hiro H0 F02 整改，登记 E1 多对一映射）**：eFuse 中的 board variant 烧在 CoreBoard 的芯片里，用户看到的 260710／260821 是 **BaseBoard** 日期码，官方扩展指南则声明适用 **1.2.1 及以上**。**`onboard/esp_mosaico.c:33–58` 显示 eFuse 的 1.1 与 1.2 同映射为 `V1_2`，是多对一映射，其他值返回错误**；variant 是软件分组，既不读取 BaseBoard，也不含 patch 版号。因此 **variant ／ BaseBoard 日期码 ／ 指南版次 三者之间的映射关系为 unknown**。到货登记三值有价值，但**只能确认该样本的观察**，**不得升级为全版次结论或版次等价结论**——本样本 confirmed 与全版次结论必须分开陈述。
