# 方案 H：背面撞针 + UART + 底座 MCU

- 日期：2026-09-20；提出：用户，整理：Claude（主控），实际模型 `claude-opus-5`。
- 定位：**产品与结构方向提案，不是硬件技术结论。** 电路、器件、电流、时序与机械由 Chrome 判定，Hiro 复核。本文不含任何工程尺寸或额定值。
- **本方案包含的需求修订已于 2026-09-20 由用户确认**（见第 5 节），`README.md` 与 `docs/PROJECT_PLAN.md` R04 已同步修订。方案 H 由候选提升为**已定方向**；方案 G 转为备选，不再并行推进。

## 1. 方案

底座在 Mosaico 落入位置的下方设置一组弹簧针（pogo），垂直压接 V1.2 背面的 7 个焊盘：

```
GND  BOOT  RST  RX  TX  5V  GND
```

底座 PCB 上设一颗小 MCU，经该 UART 与 Mosaico 通信。

## 2. 为什么它在 V1.2 之后成为最强候选：机械上零冲突

| 维度 | H（背面撞针） | G（模块常驻转接） | E（旋转 90°） |
| --- | --- | --- | --- |
| 接触方向 | **垂直下压，与「从上方落入」天然一致** | 侧向 | 侧向转轴向 |
| 耐久 | 弹簧针额定插拔寿命通常远高于机械排针（具体数值待 Chrome 依选型原厂规格确认） | 靠常驻转接规避 | 排针寿命错配 |
| 原生 USB-C | **不受影响**（背面是第三个方向，不参与左右／上下的互斥） | 不受影响 | **被埋，硬缺陷** |
| 对 `E-01` 的依赖 | **完全不依赖** | 不敏感 | 强依赖 |
| 模块槽占用 | **两个槽全部空出**，一个可给摄像头，另一个仍可扩展 | 占用一个 | 占用一个 |

其他方案的机械纠结源于「模块槽在左右、USB-C 在上下、两对面互斥」。**背面是第三个方向，不在这个互斥里。**

另有实证支持：官方开箱录屏（约 1:09）显示，实际使用中已有**透明免焊夹具带 7 根排线压接在这组焊盘上**，用于串口连接。这组焊盘是实际在用的调试／烧录接口，不是推测用途。证据见 `review/claude/hardware-revision/`。

## 3. 那颗 MCU 一颗解决四件事

7 个焊盘中 **`BOOT` 与 `RST` 均可用**，因此底座 MCU 的职责不止扫按键：

| 职责 | 说明 |
| --- | --- |
| 按键扫描 | D-pad 4 ＋ ABXY 4 ＋ L/R 2 共 10 键，经 UART 上报 |
| USB–UART 桥 | 底座插电脑即得到 Mosaico 的串口控制台。**这同时满足「底座连电脑」的产品需求** |
| 自动下载 | 驱动 `BOOT`／`RST` 做时序，**底座本身即烧录器**。对 Vibe Coding 终端属核心能力 |
| 电量与充电状态 | 读底座电池状态并上报，供 Mosaico 显示 |

器件类别上，一颗带原生 USB 的小 MCU 即可覆盖全部四项。**具体型号、供货与贴装能力由 Chrome 在 T04 中以工厂实际结果确认，本文不作选型。**

## 4. 三个必须先核实的技术点

| 编号 | 问题 | 为什么关键 | 解除方式 |
| --- | --- | --- | --- |
| H-01 | **`RX`／`TX` 是否为 UART0，是否被日志占用** | ESP-IDF 默认控制台常走 UART0。官方文档称出厂固件经 USB CDC 输出日志，**但这不等于 UART0 空闲**。若被占用，需改固件挪走日志或另选通道 | 读 BSP 与 IDF 配置；实物到货后接夹具实测 |
| H-02 | **`5V` 焊盘的载流能力** | 底座需经此给整机供电**并充电**。官方对该脚**无任何电流标注** | 官方无资料；需 Chrome 依 CoreBoard 电源链推算并在实物上验证 |
| H-03 | **7 个焊盘的间距、尺寸与表面形态** | 弹簧针位置、针头型式（平头／冠头）全依赖它。官方未给 | **只能实测**，对应测量手册第 4B.1 节 |

次级未知：弹簧针的压力与 Mosaico 外壳的承力、反复压接对焊盘镀层的磨损、底座与 Mosaico 的对位机构。

## 5. 需求修订：允许底座使用第二颗可编程 MCU

`README.md` 第一版范围与 `docs/PROJECT_PLAN.md` 写明「底座不使用第二颗可编程 MCU，通过 I²C IO 扩展器读取按键」。

**该约束在 V1.2 上已失去前提**：它成立的基础是「背部四触点提供 I²C」，而 V1.2 取消了那四个焊盘，背面只剩 UART。走 UART 必须有一端能组帧，即必须有 MCU。

用户于 2026-09-20 提出修订理由：底座本就要打板，板上多一颗控制芯片的边际成本很低。

**本文据此提出修订，但该修订属产品需求层面，须用户明确确认后方可生效，并同步修订 `README.md` 与 `docs/PROJECT_PLAN.md`。** 在确认前，方案 H 与 G 并列为候选，不作为已定方案。

修订带来的代价：两端固件需同步、需自定 UART 协议、底座固件成为新的维护对象与故障面。抵消因素：Mosaico 侧固件本就要写；底座侧职责为「扫键、转发、桥接」，复杂度低；且 PC 连接与烧录能力本身就需要底座上有能跑 USB 的器件。

## 5.1 MCU 的职责边界与失效安全（已写入 R04）

用户确认修订时提出的条件是「控制好成本和风险」。据此确立以下边界，已写入 `docs/PROJECT_PLAN.md` R04 作为验收项。

**允许的四项职责**：扫键并经 UART 上报；USB–UART 桥；驱动 `BOOT`／`RST` 做下载时序；读底座电池状态上报。

**明确禁止**：

| 禁止项 | 理由 |
| --- | --- |
| 参与供电通断的决策路径 | 供电通断必须是硬件行为，不得依赖固件执行正确 |
| 承担电池保护 | 保护属硬件职责，软件保护不构成安全手段 |
| 实现省电状态机 | 状态机是故障面的主要来源，第一版不引入 |
| 持有需要持久化的配置 | 避免固件升级与状态不一致带来的隐性故障 |

**失效安全（硬要求）**：MCU 死机、固件损坏或尚未烧录时，**Mosaico 必须仍能正常工作**，底座供电路径不得经过 MCU 的软件判断。R04 的验收项已要求在「MCU 未烧录固件」与「人为使其停机」两种状态下分别验证。

**选型纪律**：优先嘉立创常备料；优先带原生 USB 的型号以省去独立 USB–UART 桥片；不选冷门封装。**具体型号由 Chrome 定、Hiro 复核，本文不作选型。**

**协议纪律**：两端固件需同步，因此 UART 协议从第一版起即须包含版本协商字段与向后兼容规则，避免日后两端版本错配导致难以定位的故障。

## 6. 与其他方案的关系

- **H 与 G 不互斥**，但 H 占用背面、G 占用模块槽，两者同时实现会重复提供供电与输入通路，无必要。**应二选一。**
- H 若成立，模块槽两个全部空出，产品可扩展性反而更好。
- A′ 被 H 吸收：A′ 原本只解决供电与烧录，H 在其基础上加了 MCU 解决按键。
- E、E′、F 在 H 成立的前提下不再需要。
