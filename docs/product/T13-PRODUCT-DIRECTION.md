## 1. 产品定位与使用场景

按 `README.md` 与 `docs/PROJECT_PLAN.md` 第 1 节，产品是面向 Vibe Coding 的手持交互终端，游戏是附加用途。形态为长条手持设备：中间横置完整 ESP-Mosaico，左侧 D-pad，右侧 ABXY，两侧浅握把，模块可从底座拆下。Mosaico 提供屏幕、触摸、语音与无线，底座提供实体输入、电池与握持结构。

主要工作内容是“看输出、做判断、给指令”：审阅 Agent 的输出、批准或拒绝某个动作、切换任务或会话、查看当前状态。

**产品侧假设（未经使用验证）：** 这类操作高频、短促且结果重要，因此适合交给实体键，而不是每次都去点屏幕。仓库中没有用户研究或实机使用记录支撑这一判断；解除方式是硬件稳定后的实际使用观察，或由用户确认。该假设是 IR-01 优先级判定的依据之一，见第 5 节“关于优先级列”。

典型使用姿势：

| 场景 | 姿势 | 对交互的要求 |
| --- | --- | --- |
| 持续审阅与操作（主场景） | 目标姿势（尚未确认）：双手横握两侧浅握把，左拇指落在 D-pad，右拇指落在 ABXY，食指落在 L/R，屏幕位于双拇指之间 | 导航、确认、拒绝、切换上下文全部可用实体键完成，不需要抬手去点屏幕 |
| 单手持握加触摸 | 一手握住一侧握把托住设备，另一手用触摸操作 | 设备在单侧受力时仍可稳定持握；触摸目标不落在被握持手遮挡的一侧边缘 |
| 桌面放置使用 | 设备平放，以触摸和语音为主 | 放置时屏幕可视、机身稳定；是否需要防滑结构或倾角见 IR-16 |
| 边充边用 | 底座 USB-C 已插线时继续握持使用 | 线缆不干涉握持与 L/R 操作；能否边充边用属 O05／O06，本文不作任何续航或充电能力承诺 |
| 装拆模块 | Mosaico 从顶部落入槽位，由上压框固定；取出频次未知 | 本文按常规操作而非维修操作设计装入与取出（见 IR-08）；该定性依赖取出频次，在用户确认前 IR-08 的优先级为待定，见 6.3 |

**本表的性质。** 本表描述设计意图，不是已成立的握持结论。第一行的落点关系取决于 IR-01 与 IR-09 的结构判定，在 Q-01、Q-08 得到回应之前不成立，不得被引用为已确定的握持姿势。

单手场景的边界：单手只保证持握与触摸，不要求单手同时完成 D-pad 与 ABXY 的组合操作。需要双手的操作应在界面上可被识别，不应在单手场景下成为唯一路径。

## 2. 视觉语言方向

本节全部为方向性描述。任何具体色号、材料牌号、表面粗糙度、分模线位置与开孔位置均不在本文决定范围内。

**形态语言（提案，未冻结）。** 外形由功能决定，不加装饰性体块。整机左右对称，中间的模块区是视觉中心；两侧握把应当是机身的连续过渡，而不是贴上去的附加件。设备的“长条感”来自模块横置这一事实，外观上承认它，不用造型去掩盖。其中“整机左右对称”与“上压框作为可见功能件外露”两项可能约束底座内部布置（USB-C、开关、电池与 PCB 的非对称摆放），已按 IR-15 提交 Chrome 判定；在 Q-13 得到回应前，这两项不作为对结构的要求。

**表面与材质方向。** 第一版按 `docs/PROJECT_PLAN.md` 第 3 节使用打印外壳与打印键帽。表面处理方向是接受打印工艺的真实质感，而不是把打印件伪装成注塑件。握持区域与机身其余部分可通过不同的表面处理区分，让手在不看的情况下知道哪里是握把。具体材料、后处理工艺与表面参数属 Chrome 的结构文档范围，本文不决定，也不列为本文的移交条目（见 6.1）。

**配色方向（提案，未冻结）。** 机身主色方向为低饱和中性深色系，让屏幕成为唯一的高亮区域；强调色限定为单一色系，只用于少量按键或标识，不铺满机身。Mosaico 模块本体保持原有外观，不做包覆、喷涂或贴膜（R01 要求完整 Mosaico 不改板、不焊线，外观处理同样不应触及模块本体）。本文不给出任何色号；色系需在实际打印材料与样件上对照确认后才能冻结。

**模块可拆卸这一特征的外观表达（提案，未冻结）。** 可拆卸是这台设备区别于一体机的核心特征，外观上应当让人一眼看出中间是一块可以取出的模块，而不是把接缝藏起来。方向是：让模块区域的边界成为有意设计的分界（形状、表面或颜色的变化三选其一或组合），上压框作为可见的功能件呈现，而不是伪装成机身的一部分。分界的实际位置受板框、模块包络与压框结构约束，本文不指定，也不列为本文的移交条目（见 6.1）；上压框是否外露为可见功能件属 IR-15。

**指示灯与开孔的处理原则。**

- 指示灯只在用户需要知道状态时点亮，不做常亮装饰。充电、低电量等状态的指示方式需要与第 4 节的状态可见性要求一致（见 IR-07），并以该状态可被系统获取为前提（见 IR-14 与第 4 节未知项表）。
- 开孔按功能分组排列，不为了对称而增加没有功能的假孔。
- 扬声器、麦克风、USB-C、开关、指示灯的开孔位置由声学、结构与 PCB 约束决定。视觉方案接受这些位置的真实结果，不为了外观要求把它们移到别处；如果某个位置在视觉上难以接受，由 Claude 重新调整视觉方案，而不是要求 Chrome 移动开孔。

## 4. 握持时的屏幕方向与信息层级需求

本节只给原则，不给坐标、比例与像素。所有涉及屏幕可视区域、遮挡范围与落点位置的具体数值，由 Chrome 在结构确定后提交、Hiro 复核后填入。

**基准方向。** 设备以双手横握为主姿势，界面基准方向以模块横置时的屏幕水平方向为准。第一版不要求自动旋转。是否存在其他可用的装配朝向由结构决定，若结构上只允许一种朝向，界面方向随之固定。

本文不写“唯一基准方向”：屏幕可视区域的形状与长短边朝向在仓库中没有任何资料。`references/README.md` 写明“精确机械尺寸尚未冻结”，`references/` 下只有 LCSC 器件库缓存 JSON 与该 README；`docs/DESIGN_STATUS.md` 的 O01 指出模块包络与机械证据缺失；`README.md` 只确认模块“中间横置”，没有确认屏幕存在长边，也没有确认长边与模块长轴同向。在结论落定前，本节的方向表述只作为界面工作的临时基准。

**本节的未知项。** 以下各项在本文中一律记为未知，不得据此推出任何几何或功能结论。

| 未知项 | 影响 | 解除所需证据 | 提交方与确认方 |
| --- | --- | --- | --- |
| 屏幕可视区域的形状与长短边朝向 | 基准方向的表述、第 4 节全部分区方案 | 官方机械资料，或 T14 的实物测量结果 | Chrome 提交，Hiro 复核后填入 |
| 电量状态是否可被系统获取 | 常驻状态区是否包含电量；IR-07 能否成立 | 底座是否配置独立电量计的决策结果 | Chrome 提出方案与可行性判定，Hiro 复核，主控与用户确认 |
| 充电状态是否可被系统获取 | 常驻状态区是否包含充电指示；IR-07 的实现路径 | 同上，以及电源路径上的状态输出方式 | 同上 |

`docs/PROJECT_PLAN.md` 第 3 节把“电池电量显示是否配置独立计量芯片”列为待冻结决策，`docs/DESIGN_STATUS.md` 指出原生电量计不能直接代表底座电池状态。连接状态的可检测性在 `README.md`、`docs/PROJECT_PLAN.md`、`docs/DESIGN_STATUS.md` 中均未涉及，本文据此列为未知并通过 IR-14／Q-12 提给 Chrome。

**信息分区。** 屏幕按职能分为三类区域，不按固定比例划分：

| 区域 | 承载内容 | 为什么需要它 |
| --- | --- | --- |
| 常驻状态区 | 电量、是否在充电、连接状态；每一项以该状态可被获取为前提，见上表 | 产品侧判断（依赖上表未知项）：这三项对应硬件行为，用户据此判断要不要插线、要不要重新装模块 |
| 主内容区 | Agent 输出、任务内容、当前审阅对象 | 这是设备存在的理由，应占据视觉与可读性最好的区域 |
| 动作提示区 | 当前上下文下各实体键代表什么 | 实体键语义随上下文变化，没有可见对照就只能靠记忆 |

三个区域的位置与比例待屏幕可视区域和上压框遮挡范围确定后再定。

**状态指示可见原则。** 电量、充电中、连接状态三项，**若该状态可被获取，则必须在任何界面下都能被看到**，不能只存在于某个设置页面。某一项若被判定无法获取，本文不提出其可见性要求，并相应调整界面方案。

实现方式有三条路径：由屏幕常驻显示、由机身指示灯显示，或两者并用。选哪一条取决于上表中电量计与连接状态检测两项未知项的结论。本文只提出条件化的可见性要求，不指定实现方式，也不给出任何电量分级阈值。

**拇指遮挡避让原则。** 双手横握时，左右拇指的静止落点在屏幕两侧靠近握把的一带，操作 D-pad 与 ABXY 时手指还会在该带上方移动。避让原则：

- 靠近两侧的边缘带不放置需要持续阅读的正文。
- 靠近两侧的边缘带不放置不可撤销的操作控件（删除、确认执行、清空一类）。
- 不设置仅能通过触摸触发、且没有实体键替代路径的功能落在该带内。

具体避让范围取决于屏幕可视区域、握把位置与按键中心落点，属机械与布局结果，由 Chrome 提交、Hiro 复核后填入，本文不给坐标。

**替代路径原则。** 任何仅靠触摸可用的功能，都应有实体键入口或位于屏幕中部的替代入口，以应对边缘被上压框或手指遮挡的情况（见 IR-10）。

## 5. 影响硬件的交互需求清单
